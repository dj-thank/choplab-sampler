# ChopLab repository guidance

Build **おとひろい / Earth Song** for Android 10+ and Windows. Read [ROADMAP](docs/ROADMAP.md) first: it is the only current progress and acceptance index. Product contracts live in the other eight `docs/*.md` files; decisions live in `docs/adr/`. Old records remain available at `archive/pre-rebuild-v0.18.0` and are not current success evidence.

1. Start from the current Git state and the selected ROADMAP slice. State one owner, exact paths/revision, expected behavior, rollback and an observable completion condition. Preserve unrelated dirty work and user data; isolate parallel edits in separate worktrees.
2. Carry the authorized rebuild through meaningful validation and root integration. The current authorization covers stages 0–11 and PR integration; do not request the same per-PR permission again. It does not manufacture a device/provider result or human acceptance. Only the root or an explicitly assigned writer performs external mutations, release publication or device operations within that authorization.
3. Use one bounded change per PR. Branch from updated main after integration; do not push directly to main, force-push or rewrite user history. Delegation is optional, bounded and economical; no two writers own the same file or device.
4. Follow request/correction → bounded work → code and meaningful checks → readback → one current truth. Update ROADMAP with the result, unresolved failure and next action; use an ADR for durable decisions. Keep raw logs in CI/PR artifacts instead of multiplying progress ledgers.
5. Verify the affected behavior before handoff, inspect the diff, and pass required CI checks. Documentation-only changes need link/policy checks, not an APK or device run. Audio changes need the applicable [audio contract](docs/AUDIO.md); build and distribution changes need [release checks](docs/RELEASE.md).
6. Report what changed, why, validation, remaining limits and at most five useful human checks. Lead PR text in Japanese. Bind evidence to revision, artifact bytes, time, platform/route, scope and failure cases. Keep `LOCAL_PASS → DEVICE_PASS → PROVIDER_PASS → PUBLIC_PASS → HUMAN_GO` separate; screenshots, emulators, child reports and old receipts cannot substitute for actual sound, microphone or TalkBack observations.
7. Keep UI, document/editing, audio and platform I/O separate. The planned EngineCore serves playback and export; preserve start-inclusive/end-exclusive frames, stereo channel identity, bounded inputs and reversible edits. No allocation, blocking locks, I/O, logging or networking in render; measure rather than assume real-time safety.
8. Preserve the user-selected original four-stage instrument UI with large PADs and the option2 linked arrangement; follow docs/DESIGN.md, not the rejected five-screen card or shelf-centered redesign. UI uses ja/en resources and typed core notices. Keep legacy behavior during the staged migration; remove old paths only after their replacements and protection tests work. No DRM/capture-policy bypass or proprietary product assets/trade dress.
9. Never commit audio, projects, models, credentials, private keys, personal paths or device identifiers. Public certificates/fingerprints are distinct from private signing material. Scan source/history and packaged artifacts; preserve signature, version, hash, archive and dependency controls. Record added dependencies in [NOTICE](NOTICE.md).
10. Release tags originate from main and follow the authorized release scope. Do not fall back silently to debug/unsigned distribution. Keep Preview data and signing separate from the existing app. Use [TESTING](docs/TESTING.md) and [RELEASE](docs/RELEASE.md) for exact boundaries; current files and fresh readback outrank historical claims.
