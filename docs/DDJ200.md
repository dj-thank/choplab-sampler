# DDJ-200 — Android sampler controller preview

## Status / evidence boundary (2026-09-16)

This is an opt-in Android controller implementation on top of PR #101 at
`6a508d3802ba11f6f6858270891ab48519282c6c`, not a verified hardware certification,
a new release, or a Windows/iOS MIDI adapter. Existing audio DSP and project
formats are unchanged. The shared mapping can be reused by a future desktop
adapter; that does not make desktop MIDI available today.

The MIDI decoder/session has 31 passing supplemental host test bodies using
Kotlin CLI 1.9.0 and OpenJDK 21.0.11. Only the `kotlin.test.Test` import and
annotations were removed in a temporary runner; production `Ddj200.kt` and
all assertion bodies were unchanged. This is NOT the supported Gradle/JUnit,
Android/Compose, physical DDJ-200, latency or sound-quality gate. The Android
adapter, UI, controller bridge and manifest have source review only locally.
See [receipt](../outputs/ddj200-host-20260916.txt) and the
[active plan](../plans/active/ddj200-controller-20260916.md). Read this change's

## Connect

Build this feature branch's Android APK, then open the **DDJ-200** button above
the deck. For USB, use a data-capable cable and a phone USB-host connection,
press **USBを再検索**, and select the listed DDJ-200. If the phone cannot power
the controller, use a suitable powered host hub. For BLE, power the controller,
close another app's existing connection, press **Bluetoothを検索**, grant the
requested permission, and explicitly select the device. Discovery stops after
10 seconds; opening times out after 12 seconds. No automatic pairing, scanning,
permission prompts or MIDI service lookup occurs at app startup.

USB discovery does not require Bluetooth permission. Android 12+ BLE uses the
Nearby devices scan/connect permissions; Android 10/11 uses foreground location
permission and the OS location setting for BLE discovery. No location or Bluetooth
address is stored or transmitted by this adapter. Audio continues to use the
phone's existing output route: this is MIDI control, not DDJ audio output.

Closing the dialog leaves the selected controller connected. Backgrounding,
rotation/disposal, explicit disconnect, USB removal or receive overflow closes
that connection and stops playback; return to the dialog to reconnect. A revoked
permission or failed scan remains a visible error, not a silent success.

## Sampler mapping (not a two-deck DJ mixer)

| DDJ-200 control | Otohiroi action |
| --- | --- |
| Left / right performance PADs | Current BANK's PAD 1–8 / 9–16 |
| SHIFT + left / right PADs | Current BANK's PAD 17–24 / 25–32 |
| Left / right SYNC | Previous / next BANK A–D, wrapping |
| SHIFT + left / right SYNC | Undo / Redo |
| Left / right PLAY | Toggle source playback / BEAT transport |
| CUE or SHIFT + PLAY | ALL STOP |
| SHIFT + CUE | Existing sequence record-arm action; may start BEAT transport |
| Left / right jog top touch + rotation | Source-range / selected-PAD scratch |
| Left / right TEMPO | Source pitch −12…+12 semitones / BPM 40…240 |
| Channel fader | Gain 0…150% of the last PAD pressed on that side |
| COLOR FX | TONE 0…1 of the last PAD pressed on that side |

PADs retain their existing ONE SHOT/GATE/LOOP, recording-admission and choke
semantics. Populate PADs using the existing capture/chop UI; this profile does
not introduce destructive capture shortcuts or full DJ decks. The right jog
uses the app's single selected-PAD scratch engine; it is not an independent
audio deck. Avoid simultaneous on-screen and hardware scratch gestures until
physical interaction validation is complete. Jog gain is an initial mapping,
not a measured calibration, and source playback uses the existing manual-resume
behavior after scratching.

Tempo, faders and COLOR FX use soft takeover: move through the current software
value before it follows the hardware. A PAD change resets its knob takeover,
and a software-value change beyond the 2.5% deadband revokes the latch. Fader
and TONE controls remain inactive until a PAD on that side has been pressed.
PAD release retains the original PAD index and trigger token across BANK/SHIFT
changes, so an old MIDI release does not stop a newer touch-triggered voice.

**Not mapped:** crossfader, three-band EQ, headphone cue/split monitoring,
transition FX, fader-start, wheel rim pitch bend, MIDI clock/sync and output LED
synchronization. No claims are made for Bluetooth audio latency, beatmatching,
physical jog sensitivity or Windows/iOS MIDI connectivity.

## Implementation and verification

`shared/.../midi/Ddj200.kt` owns incremental MIDI 1.0 parsing, official channel
mapping, held buttons, token-pinned releases, fresh 14-bit CC pairs and pickup.
`Ddj200DeckTarget.kt` delegates through `SamplerDeckController` and reads current
`SamplerUiState`, retaining engine admission, autosave and undo behavior.
`app/.../midi/AndroidDdj200.kt` owns device discovery, asynchronous open epochs,
ports, timeouts and permission/error handling. Android supplies unframed MIDI
bytes; the parser does not reinterpret USB event headers or BLE timestamps.
The receive queue is bounded to 32 packets of at most 4096 bytes, with UI-thread
command dispatch and overflow disconnect. No application audio callback is changed.
`Ddj200Controls.kt` provides the connection/status/help dialog; `SamplerScreen.kt`
adds the opt-in entry point without modifying the shared deck's internal layout.

Required supported-toolchain checks:

```sh
./scripts/doctor.sh
python3 scripts/check_public_surface.py
./scripts/validate_project.sh
./gradlew :shared:testAndroidHostTest :shared:desktopTest \
  :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
```

Local container checkout/Gradle acquisition was blocked by DNS and no Android
SDK was installed. The repository-wide doctor, public-surface scanner, validation,
Gradle, lint, APK and UI tests were not run locally. New plain-text change
candidates were separately checked for secret patterns and XML syntax; that is
not a replacement for the repository-wide public/history scan.

Physical acceptance must cover USB and BLE separately: all PADs/BANKs/SHIFT
releases, chords and rapid repeats, GATE/LOOP release, touch retrigger, jog stop
and release, parameter pickup after screen edits, permission deny/revoke,
Bluetooth off, scan/open cancellation, plug/unplug, background/rotation,
long-session stability, output routes and measured latency. Keep the PR draft
until the supported build is green and record real-device results explicitly.

## Primary specifications

- AlphaTheta DDJ-200 MIDI Message List E2, page 2 (official table, inspected 2026-09-16):
  https://downloads.support.alphatheta.com/software_info/dj-controllers/DDJ-200/DDJ-200_MIDI_Message_List_E2.pdf
- Android MidiManager (openDevice/openBluetoothDevice/device callbacks):
  https://developer.android.com/reference/android/media/midi/MidiManager
- Android Bluetooth permissions:
  https://developer.android.com/develop/connectivity/bluetooth/bt-permissions

The manufacturer's normal PAD channels are 8/10, shifted channels 9/11
(one-based); deck buttons use 1/2 and COLOR FX uses 7. Do not replace these with
common keyboard notes or guessed deck-channel PADs. Jog 64 is neutral, above
64 positive, below 64 negative. Mapping tests lock these byte-level contracts.
